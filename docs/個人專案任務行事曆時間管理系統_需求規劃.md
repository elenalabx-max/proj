# 個人使用的專案＋任務＋行事曆＋時間管理系統 — 需求規劃書

你現在要協助我建立一套「個人使用的專案＋任務＋行事曆＋時間管理系統」。

這不是多人團隊協作系統，不需要做成 Monday.com 那麼複雜。
目前主要使用者只有我自己，但系統仍必須具備帳號登入、雲端資料庫、不同裝置同步能力。

請先完整理解以下需求，再進行架構規劃與開發。

## 一、產品核心定位

這是一套結合：

1. 專案管理
2. 任務管理
3. Todo
4. Reminder
5. Calendar
6. 四象限時間管理
7. 交辦追蹤
8. 收集箱
9. 遺忘箱
10. 實際工時紀錄
11. 專案工時統計

的個人工作管理系統。

核心理念是：

「未完成，不代表現在需要出現在我眼前。」

事情即使尚未完成，也可能處於：
- 收集箱
- 今天
- 未來排程
- 專案
- 待他人
- 待我確認
- 遺忘箱

只有「現在真的需要我處理」的事情，才應該出現在主要 Today 畫面。

## 二、建議技術架構

希望採用：

Frontend：
- Next.js
- TypeScript
- Tailwind CSS

Backend / Database / Auth：
- Supabase
- PostgreSQL
- Supabase Auth
- Supabase Realtime

其他可使用：
- date-fns
- dnd-kit
- rrule 或其他成熟 recurrence library

必要條件：

1. 不可以將主要資料只存在 localStorage。
2. 所有主要資料必須寫入雲端資料庫。
3. 同一帳號登入不同裝置時，要看到相同資料。
4. 電腦新增或修改資料後，手機應同步看到。
5. 手機修改後，電腦也應同步。
6. 所有資料必須和 user_id 綁定。
7. 使用 Supabase Row Level Security 確保使用者只能看到自己的資料。

登入方式 V1：
- Email + Password
- Google Login

## 四、Area：個人 / 工作

系統最上層分成：

1. Personal 個人
2. Work 工作

所有 Task 可以歸類到其中一個 Area。

左側篩選可以：

```
☑ 個人
☑ 工作
```

工作底下還可以勾選 Project：

```
☑ 工作
   ☑ 台北PBC
   ☑ 學刊
   ☐ 高公局
   ☐ 其他專案
```

可以同時勾多個 Project。

例如：

勾選：
☑ 台北PBC
☑ 學刊
☑ 個人

Calendar 就同時顯示以上內容。

Project 是 Area 內的篩選條件，不應因為勾選多個 Project 就產生很多 Calendar 欄位。

## 五、顏色系統

這是必要功能。

### 【Personal】

個人 Area 可以設定自己的「預設顏色」。

例如：

Personal Default Color = 柔紫色

所有沒有另外設定顏色的個人 Task / Todo，在 Calendar 上預設使用這個顏色。

使用者可以到：

設定 → 顏色 → Personal 預設顏色

自由修改。

### 【Work】

Work 不使用一個統一顏色。

每一個 Work Project 都可以設定自己的預設顏色。

例如：

- 台北PBC = 藍色
- 學刊 = 綠色
- 高公局PBC = 橘色
- 系友會 = 紫色

Project 建立或編輯時要有：

Project Color

欄位。

此 Project 下的 Task 預設繼承 Project Color。

例如：

Project：台北PBC
Color：#4A90E2

底下：
- 半年分析報告
- 年度總結報告
- 委員意見
- 會議

Calendar Block 都使用台北PBC顏色。

V1 不需要強迫每一個 Task 都自己選色。

規則（2026-09-02 修正，跟原始規劃不同）：

- 有掛 Project（不分 Personal 或 Work）→ 一律繼承 Project Color
- 沒掛 Project 的 Personal 項目 → 使用 Personal Default Color
- 沒掛 Project 的 Work 項目 → 使用 Work 的 fallback 預設色

原始規劃是「Personal 一律用 Personal Default Color、不管有沒有掛 Project」，但
Personal Project 本來就能個別設定顏色（跟 Work Project 一樣），Calendar 卻不會
反映，等於白設，所以改成 Personal／Work 用同一套「有掛 Project 就用 Project
顏色」規則，只有「完全沒掛 Project」時才退回到區塊預設色。這條規則不只適用
Task，Todo／Reminder 掛了 Project 也是同一套邏輯（見十、十一節）。

未來可以擴充 Task Color Override，但 V1 可以先不做。

色彩選擇介面：
- 提供數個預設色票
- 同時允許 custom color picker

所有顏色必須支援：
- Light Mode
- Dark Mode
- 文字對比可讀性

## 六、Project 定義

Project 是有明確成果或持續一段時間的工作集合。

例如：

工作：
- 台北PBC
- 高公局PBC
- 學刊

個人也可以有 Project，例如：
- 博士
- 日本旅行
- 居家整理

Project 至少包含：

```
id
user_id
area
name
description
color
status
category   -- 2026-09-02 新增：自由文字，例如「林老師」「桃園市政府養工處」
owner      -- 2026-09-02 新增：業主／窗口，自由文字
start_date
due_date
created_at
updated_at
archived_at
```

Project Status 建議：

```
active
paused
completed
archived
```

Project 詳細頁面顯示的屬性（2026-09-02 定案）：狀態、類別、業主、執行期間
（start_date–due_date）、Task 完成度。所有基本資料集中在一個「編輯」按鈕開啟
的對話框裡一次修改（名稱／Area／顏色／狀態／類別／業主／執行期間），不是每個
欄位各自即時輸入即時存檔。

Project 可以顯示：

- Task 數 / 已完成 Task / 未完成 Task / 完成度（進度條）
- Todo 完成度、Reminder 完成度（各自的完成/總數 + 進度條，2026-09-02 新增）
  ——預設只顯示總覽，明細清單要點「查看明細」才彈窗看，避免清單一長就把整個
  頁面拉很長；明細裡未完成的排最上面
- 預計總工時 / 實際總工時（僅 Task，Time Log 加總）
  ——同樣預設只顯示總覽卡片，各 Task 的工時明細也是點「查看明細」才彈窗看，
  依「實際超出預計的量」由大到小排序
- Tasks 清單本身可以依狀態篩選、依建立時間／狀態／標題排序，新增輸入框在
  清單最上面

（原規劃提到的「進度百分比」已拆成 Task／Todo／Reminder 三個獨立完成度，
不是單一數字——三種東西的「完成」意義不同，混在一起算不出有意義的百分比。）

title

## 八、Task Status

不要只做：未完成 / 完成

要有：

1. inbox
2. todo
3. in_progress
4. waiting
5. review
6. completed
7. forgotten

中文顯示：

- 收集箱
- 待處理
- 進行中
- 待他人
- 待我確認
- 完成
- 遺忘

其中：

waiting：我已經交辦別人，目前不是我要執行。

review：對方完成，或到了 Follow-up 時間，需要我確認。

completed：我確認事情真正結案。

## 九、Subtask

Subtask 是 Task 底下的小步驟。

例如：

Task：完成年度成果報告

Subtask：
- □ 更新表1-1
- □ 更新表1-2
- □ 修改1.1
- □ 修改1.2
- □ 整理委員意見
- □ PDF確認

Subtask：
- 必須屬於 Task
- 可以勾完成
- 可以記 Time Log
- 預設不單獨出現在 Calendar

如果某個 Subtask 需要：
- 獨立日期
- 獨立排程
- 獨立 Deadline
- 獨立交辦

應提供：「轉成 Task」功能。

## 十、Todo

Todo 是很小、很單純的待辦。

例如：
- 買洗衣精
- 換圖書館密碼
- 問學長照片
- 買收據夾

Todo 不要求：
- 開始時間
- 結束時間
- 工時

Todo 可以（不強迫）掛 Project（2026-09-02 調整，原規劃是「不要求 Project」，
但「todo 比較像小雜事，可以歸類到 Project 或 Personal/Work」——掛了 Project
不會讓 Todo 變成 Task，還是沒有排程／Subtask／工時那些機關，純粹貼標籤用）。

Todo 實際欄位（2026-09-02 定案）：

```
id
user_id
area_id       -- 可為 null
project_id    -- 可為 null，2026-09-02 新增
title
date          -- 可為 null，null 就在 Inbox
forgotten_until
recurrence_rule_id  -- 2026-09-02 新增，見二十五節
important     -- 2026-09-02 新增，跟 Task 一樣可以進四象限
urgent        -- 2026-09-02 新增
completed_at
archived_at   -- 2026-09-02 新增，軟刪除，可從 Settings → 封存 復原或永久刪除
```

也可以沒有日期而存在 Inbox。

Todo 可以：
- 加 Reminder
- 排入 Today
- 排入某天
- 放入 Forgotten（含到期自動判定的「逾期未完成」，見十三節）
- 轉成 Task
- 設定重複（見二十五節）
- 標記重要／緊急、進四象限（見二十四節）
- 刪除（軟刪除，進封存，可復原或永久刪除）

Todo 的 Time Log 為選用功能，不強迫填。

## 十一、Reminder

Reminder 不是 Task。

Reminder 的目的只有：「在某一個時間提醒我。」

Reminder 可以：
1. 獨立存在
2. 掛在 Project
3. 掛在 Task
4. 掛在 Todo

例如：

Task：完成半年分析報告

Reminder：9/3 09:00 提醒我處理

Reminder 至少包含：

```
id
user_id

remind_at
is_all_day        -- 2026-09-02 新增，整天提醒不用挑時間

linked_type
linked_id

title
note

recurrence_rule_id  -- 2026-09-02 新增，見二十五節
important           -- 2026-09-02 新增，可以進四象限
urgent               -- 2026-09-02 新增

completed_at
```

Reminder 沒有 archived_at——刪除是真的 Hard Delete（見四十二節的例外說明），
跟 Task／Todo／Project 的軟刪除不同，這是刻意的，因為提醒本質上很輕量、
用完即丟，不需要進封存區。

Reminder 逾期未完成（時間點過了、跨過 0 點還沒勾完成）也算自動遺忘的一種，
邏輯跟 Task／Todo 一致，見十三節。

## 十二、收集箱 Inbox

Inbox 是：「想到事情，但是還沒決定怎麼安排。」

使用者快速新增事項時，可以只輸入：標題

不用強迫選：Project / 日期 / 時間 / 重要性

建立後先進 Inbox。

Inbox 每筆事情應有快速操作：

```
[今天] [明天] [選日期] [加入專案] [遺忘]
```

支援批次：

```
☑ A
☑ B
☑ C

→ 移入 Project
→ 排到某一天
→ 放入 Forgotten
```

## 十三、遺忘箱 Forgotten

Forgotten 是：「這件事還沒有完成，但我現在完全不想看到。」

與 Completed 完全不同。

Forgotten 支援兩種：
1. 無限期遺忘
2. 遺忘到某一天

例如：

研究 AI 工具
Forgot Until：2026/10/01

在 10/1 前：
- 不出現在 Today
- 不出現在 Calendar
- 不出現在普通 Todo

10/1 到期後：自動回到 Inbox，並提示：「之前擱置的事情，要重新安排嗎？」

Forgotten 不需要一直顯示紅色未完成數量。

自動遺忘子類型（2026-09-02 定案）：Task／Todo／Reminder 只要「有設定期限或
排定時間、且已經過期還沒完成」，即使使用者沒有手動勾選遺忘，也會自動算
Forgotten 的一種，直接列在 Forgotten 頁面、用「逾期」標籤跟手動遺忘的區分開來。
判斷一律用「日期」比對、不用精確時間——今天 14:00–16:00 的任務過了 16:00
但還是今天，不算逾期；要跨過 0 點、變成昨天的事才算。這種「想先不看，但還
沒有規劃日期」的東西應該放 Inbox，不是 Forgotten——Forgotten 專門處理「已經
有期限、但確實逾期沒做」的情況。

自動逾期的還原動作跟手動遺忘不同：手動遺忘只要清掉 forgotten_until；自動
逾期的沒有 forgotten_until 可清，要把 due_date／scheduled_date（Task）或
date（Todo）一起清掉，不然一放回 Inbox 又立刻被判定成逾期。Reminder 沒有
「無日期」狀態，回到不逾期的動作是打開它的詳細面板讓使用者自己決定要改時間
還是勾完成，不會自動幫他猜一個新時間。

## 十四、交辦 / Waiting

即使系統目前只有我自己登入，我仍然會把工作交辦給別人。

例如：請奕賢修改報告。

對方不需要擁有系統帳號。

我要可以自己建立 Person：
- 老師
- 奕賢
- 廠商
- 監造
- 機關承辦

Person Table：

```
id
user_id
name
note
```

Task 可以指定：Assignee

例如：

Task：修改期末報告
Assignee：奕賢

交辦後：status = waiting

這件事情不應該繼續占據我的 Today Todo。

## 十五、Deadline 與 Follow-up 必須分開

非常重要：

「對方應該完成的時間」和「我要確認的時間」不是同一件事。

例如：

請 A 9/5 前給資料。

delegate_deadline：9/5 17:00

但：

follow_up_at：9/4 15:00

9/4 15:00：系統提醒我：「A 的『PBC統計資料』明天到期，要不要確認進度？」

如果對方還沒完成：我可以按：延後追蹤

例如：明天 10:00 再確認。Task 回到 waiting。

到了新的 Follow-up：再出現在 Review / 待確認。

## 十六、Today

首頁預設應為：Today，而不是 Project List。

Today 主要回答：「我今天到底要做什麼？」

Today 可以看到：
1. 今天排程
2. 今天 Todo
3. 今天需要 Follow-up
4. 今天 Reminder

但 Waiting 中尚未到 Follow-up 時間的事情：不要一直占 Today。

## 十七、Calendar

Calendar 必須有：Month / Week / Day 三種檢視。

## 十八、Day View

Day View 有兩種模式：
1. Timeline
2. Eisenhower Matrix 四象限

上方切換：

```
[時間軸] [四象限]
```

2026-09-02 調整：這個切換只留在 Today 頁面的 Day Timeline。Calendar 底下
的 3 Days 頁面拿掉了這個切換，只剩時間軸——使用者認為 Calendar 那邊不需要
四象限（四象限本來就是「當天」的另一種呈現方式，Today 頁面已經有了，
沒必要在 Calendar 重複一份）。

## 十九、Day Timeline 特殊版型

這是核心 UI。

Day Timeline 必須做成：

左側：Work
右側：Personal

兩邊共用同一條時間軸。

例如：

```
時間       工作                    個人

整天     PBC發文                  繳信用卡

09:00    修改報告

10:00                            博士論文
11:00

13:00    委員邀請信

14:00    PBC會議

15:00                            運動
```

Work 固定左側。
Personal 固定右側。

這叫：Two-lane Timeline

Project 不增加額外欄位。

例如勾選：

Work：☑ 台北PBC ☑ 學刊
Personal：☑ 博士

仍然只有：Work | Personal 兩欄。

Work 欄內同時顯示：台北PBC / 學刊

不同 Project 使用各自 Project Color。

沒掛 Project 的 Block 才使用 Personal Default Color／Work fallback 色
（見五節 2026-09-02 修正後的規則）。

實際實作是「3 Days」而不是單一 Day（2026-09-02 定案，使用者要求），同一顆
`MultiDayTimeline` 元件吃 1~3 天，每天內部仍然固定 Work｜Personal 兩欄，這條
規則不因為天數變多而改變。手機寬度（< 768px）時 3 Days／Week 會自動收成只
顯示當天一天，左右箭頭改成逐日翻頁，桌面版不受影響。今天所在的那一欄／
那一天會有明顯的黑底白字「今天」標籤，不只是文字顏色差一點。

Todo 獨立一排（2026-09-02 新增）：Todo 沒有時間，畫不進 Work｜Personal 的
時段格子，原本整個時間軸完全看不到 Todo。改成在日期標題下面、Work｜Personal
欄位標籤上面，加一排「Todo」，同一天的 Todo 用色點膠囊(pill)並排顯示，
顏色跟著分類走；點一下：本體（有自己那一筆資料的）會打開對應的 Todo 詳細
面板編輯，跟全天 Task／提醒同一套邏輯；重複展開出來的那一次沒有自己的資料
列，點一下直接切換完成。

## 二十、Area 顯示切換

使用者可以：☑ Work ☑ Personal

如果兩個都選：50% / 50%（Work | Personal）

如果只選 Work：Work 自動使用 100% 寬度。

如果只選 Personal：Personal 自動使用 100% 寬度。

（開發過程中曾經多加過「每個 Project 各自一個眼睛圖示可以單獨開關」，
2026-09-02 拿掉了——使用者認為只要 Work／Personal 兩個總開關就夠，不需要
再細分到每個 Project。等於是回到這裡最原始只有兩個 checkbox 的規劃。
Today 頁面的 Day Timeline 更進一步，連這兩個總開關的篩選列都整條拿掉，
因為 Today 本來就固定顯示 Work｜Personal 兩欄，篩選列在那邊沒有意義。）

## 二十一、Calendar Block 操作

Task Block 必須支援：
1. Drag & Drop
2. 上下移動改時間
3. 跨日期移動
4. Resize

例如：

14:00–15:00

拉長：

14:00–17:00

scheduled_end 自動更新。

Calendar 上拖曳應更新資料庫。

如果不同裝置開著：透過 Realtime 同步更新。（V1 尚未實作 Realtime，見四十三節）

拖曳／縮放已加上 `touch-action: none`，觸控裝置上不會被瀏覽器預設的整頁滾動
手勢打斷（2026-09-02）。

點空白處新增 Task（2026-09-02 定案）：不會直接跳出 Task Detail Panel——手滑
點到空白處很常見，開面板反而是額外的清理負擔。改成畫面下方跳一個約 6 秒的
提示條「已新增「新任務」，點這裡編輯」+ 一鍵「刪除」，误點可以立刻復原，
真的要編輯就點提示或直接點色塊。

## 二十三、Due Date 與 Scheduled Time 必須分開

非常重要。

例如：

但我要：9/3 14:00–17:00 進行修改。

資料應分成：

```
due_date = 9/7

scheduled_date = 9/3
scheduled_start = 14:00
scheduled_end = 17:00
```

不要只設計一個 date 欄位。

## 二十四、四象限

Task、Todo、Reminder 都有兩個 Boolean：important / urgent（Todo／Reminder
是 2026-09-02 新增的，原本只有 Task 有）。

產生四象限：

- 重要＋緊急
- 重要＋不緊急
- 不重要＋緊急
- 不重要＋不緊急

四象限模式不要再切 Work / Personal。否則會變八格。

四象限現在混合顯示當天的 Task／Todo／Reminder 三種（2026-09-02），每張 Card
顯示：

```
Task/Todo/Reminder Name
Task/Todo/提醒（種類標籤）
Area · Project（如果有掛）
```

例如：

```

Task · 工作 · 台北PBC
```

```
拿蝦皮
Todo · 個人 · 雜事
```

```
11:00 買水壺
提醒 · 個人 · 雜事
```

三種都可以拖曳到另一個象限，系統自動修改對應那筆資料的 important/urgent
（用種類 + id 一起記錄拖曳中的項目，確保放開時改到正確的表）。

例如：重要不緊急 → 拖到重要且緊急，系統自動修改 urgent。

## 二十五、重複任務

Task、Todo、Reminder 都可以設定 Recurrence（Reminder 是 2026-09-02 新增的，
每次重複沿用同一個「幾點幾分」，只換日期；Todo 比 Task 簡單，沒有時間、
沒有全天概念，只有「哪一天」跟「完成了沒」）。

例如：每天 / 每週 / 每月 / 每年 / 自訂

設定方式可以包含：

```
每天

每週：星期一 星期三 星期五

每月：每月5日

每年：每年9月1日
```

必要規則：

Recurring Task 每一次出現必須是獨立 Instance。

例如：每月5日整理帳務。

9/5 10/5 11/5 12/5 是四個獨立 instance。

9/5 勾完成：只影響 9/5。

絕對不可以把 10/5 11/5 12/5 一起改成完成。

同樣地：修改 9/5 這次 Task 的內容，預設只修改此次。

系統可以詢問：

```
只修改此次
修改此次及未來
修改全部
```

但「完成」永遠只完成單次 Instance。

實作範圍現況（2026-09-02 全部補齊）：重複展開（把 recurrence_rule 換算成某段
日期範圍內的每一次 occurrence）已經接到 Today、Calendar 的 3 Days／Day 時間軸、
Week、Month、四象限。四象限比較特殊：important/urgent 是「這個系列」的屬性、
不是像完成狀態那種要分次記錄的東西，所以拖曳重複展開出來的那一次一律改到
master 那筆，等於是重新分類整個系列，不是只改這一次。

## 二十六、工時管理

這是核心功能。

必須明確分開：Estimated Time / Scheduled Time / Actual Time

例如：

```
預計：2 hours
排程：14:00–16:00
實際：3 hours 20 minutes
```

三者不能混用。

Estimated Time 的來源（2026-09-02 調整）：改排定時間（Detail Panel 的時間
選擇器、Calendar 拖曳/縮放、點空白處新增）時，Estimated Time 自動重算成
「排定時段的長度」，不用使用者自己再填一次數字。這是「先幫你算好，你還是
可以手動改」的預設值，不是鎖死——手動改過 Estimated Time 之後，只要再動一次
排定時間，還是會被蓋回排定時段的長度。

## 四十八、重要 UX 原則

5. Calendar 的排程時間不是實際工時。
6. Actual Time 必須來自 Time Log。

8. Personal / Work 在 Day Timeline 必須左右分欄。

10. 新增 Task 要快，不能每次強迫填十幾個欄位。
